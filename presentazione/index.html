Un server condiviso per la ricerca del Dipartimento

Obiettivi, servizi possibili e le vostre esigenze

Riunione di Dipartimento · ottobre 2026

Durata prevista circa 45 minuti (15 di presentazione, 30 di discussione). Lo scopo non è presentare una soluzione già decisa, ma raccogliere le esigenze dei gruppi prima di scegliere la soluzione tecnica.

L’obiettivo

Uno spazio comune per ospitare dati e servizi usati nei diversi progetti di ricerca.

Pensato per l’intero Dipartimento, non solo per il Laboratorio.

Ripartire dalla mail inviata al Dipartimento. L’iniziativa nasce da esigenze già emerse negli scorsi anni nel Laboratorio, ma la progettazione non deve essere dettata solo da quelle.

Perché un server condiviso

Il problema

I progetti producono piccoli dataset che, per essere accessibili, richiedono un po’ di infrastruttura. Alla fine del progetto i costi non sono più sostenibili.

L’idea

Poiché i dataset sono piccoli, accorpiamo i costi e gestiamo una sola infrastruttura per tutti.

Questo è il motivo per cui il server esiste: dare una casa duratura agli output dei progetti dopo la fine dei finanziamenti. Dataset piccoli, quindi poche risorse da condividere.

Cosa è, cosa non è

È

  • Un’infrastruttura server condivisa
  • Uno spazio per dati e servizi di ricerca
  • Un luogo per pubblicare gli output dei progetti
  • Una risorsa a disposizione di tutti i gruppi

Non è

  • Un’infrastruttura di calcolo
  • Un cluster per training o elaborazioni pesanti
  • Una soluzione già decisa nei dettagli tecnici
  • Un servizio solo per il Laboratorio
Sottolineare subito che non si tratta di calcolo: niente GPU o code di job.

Le esigenze emerse finora

Consultare corpora

NoSketch Engine per interrogare i corpora, anche con accesso riservato.

Pubblicare pagine

Siti statici di presentazione e navigazione degli output di ricerca.

Ospitare dati

Un luogo stabile per dati e risorse, oltre il singolo progetto o portatile.

E le vostre? Queste vengono dal Laboratorio. Il punto della riunione è scoprire cosa serve agli altri gruppi.

Come potrebbe funzionare

Utenti

Browser, un solo dominio

→

Caddy

Un indirizzo per servizio, HTTPS automatico

→

Servizi

Un container Docker per ciascuno, aggiornabili separatamente

Tutto descritto in Docker Compose: riproducibile, documentato e spostabile su un’altra macchina.

Ogni servizio è isolato, quindi aggiungerne uno nuovo non rompe gli altri. Rimandare alla demo.

Uno spazio per ogni gruppo

Indirizzi separati

Ogni progetto o gruppo ha il suo indirizzo, ad esempio un sottodominio dedicato.

Permessi propri

Chi può modificare e chi può solo consultare lo decide ciascun gruppo.

Gestione condivisa

Backup, aggiornamenti e monitoraggio sono gestiti una volta sola, non da ogni gruppo.

Restano aperte le domande su chi amministra il server e come si decidono le richieste di spazio. Le portiamo in discussione, non le decidiamo noi.

Solo dati con licenza aperta

  • Ospitiamo solo dataset con licenza open source o aperta
  • Non abbiamo le competenze per gestire livelli di sicurezza avanzati
  • Niente dati riservati o sensibili
Scelta di prudenza: un’infrastruttura gestita da pochi non può garantire sicurezza avanzata, quindi il perimetro è ciò che è già pubblico per licenza. Chiarire il caso dei corpora ad accesso riservato citati tra le esigenze: restano compatibili solo se la licenza lo consente.
